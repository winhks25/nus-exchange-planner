## Execution rules

The required order is **runtime changes → local verification → metadata table deletion (`supabase db push`) → immediate verification → cleanup/refactoring → final regression**. Local tests and an export/restore rehearsal are prerequisites to table deletion. A compatible-runtime *deployment* is no longer a prerequisite, because the runtime is not redeployed; instead the compatible core-readiness runtime must be proven on localhost (US1) before the deletion. Do not interpret the final regression phase as permission to postpone all testing until after destructive DDL.

Only the five explicitly named tables are deletion targets. Do not broaden a drop based on a prefix match. Preserve eight core tables, their records, and every core column except `module_mappings.source_row_id`. Retain source presentation/order fields; they affect API parity even though their names begin with `source_`.

Planning is complete when this document is written; implementation is complete only when all tasks below have evidence. Mark each task checked only after its own acceptance criteria are met. Record unavailable access or tools as blockers rather than claiming success. Production schema changes require the selected target, migration, and recoverable export to be established by the tasks below, plus the compatible core-readiness runtime proven on localhost. No deployed application version is required.

`REMOVAL_MIGRATION` below refers to the CLI-generated file `supabase/migrations/20261024034234_remove_catalog_metadata.sql` (created in T027). `PRIVATE_BACKUP_DIR` is a private durable directory outside Git selected and recorded in T007, never an environment variable containing a credential.

## Implementation strategy

US1 is the smallest safe increment: the runtime no longer needs metadata permissions while the old tables remain, and this is proven on localhost. US4 retires the importer and cleans up only after behavior is verified. US5 proves the final cleaned-up implementation runs correctly on localhost in both backend modes. No application deployment is performed at any phase. Do not stop at the MVP when executing the full request.

Baseline expectations are captured before implementation and remain independent of the new code. The old JSON dataset and the repaired PostgreSQL dataset have legitimate differences; each mode must be tested against its own documented expectations. No source-data correction is part of this feature.
