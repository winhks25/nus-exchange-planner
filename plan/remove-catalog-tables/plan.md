## Runtime design

In `backend/app/repositories/postgres_catalog.py`, remove `PUBLISHED_BATCH_SQL` and `_require_published_batch`. Use one small parameterless readiness query over `degrees` and `partner_universities`, within the existing read transaction, at each operation's entry. Its boolean condition is: degrees exist, universities exist, and no degree has a null `full_title`. Missing schema or denied required-table access still produces the existing sanitized database error. Do not query `pg_catalog` on every request or keep a cached readiness flag that can become stale.

Keep the existing business SQL and response construction unless a measured correctness issue requires an adjustment. Keep the defensive validation of returned catalog rows. Valid databases with no mappings still support zero-count recommendations and empty results. Readiness is deliberately narrower than historical source reconciliation; direct data editors must use transactions for multi-table changes. Document this limitation instead of inventing a replacement batch table.

Keep `CATALOG_BACKEND=json|postgres`, default local JSON behavior, dependency injection, JSON files, and explicit rollback. Existing production configuration is recorded as PostgreSQL with the `catalog_reader` role. Role names are outside the table-removal request.

## Schema and migration design

Use Supabase guidance and current CLI `--help` when implementation starts. Create the migration with `supabase migration new remove_catalog_metadata`; record its actual generated path in the task document and deployment record. Do not invent a timestamp or edit applied migrations. For local iteration follow the repository's Supabase skill: iterate DDL without adding migration-history entries, generate/reconcile the final migration through the supported workflow, and inspect it before applying. Keep the version generated by the CLI and ensure exactly the intended new change is pending for production.

Migration changes are explicit and transactional:

- Drop `module_mappings_source_row_id_fkey` and `module_mappings_source_row_id_key`, then `module_mappings.source_row_id`.
- Drop `public.catalog_issues`, `public.catalog_repairs`, `public.catalog_source_rows`, `public.catalog_source_snapshots`, and `public.catalog_import_batches` in that order (the first two are interchangeable).
- Dropping the archive tables removes their attached triggers, policies, indexes, and owned identity sequences. After confirming no other dependencies, drop `public.reject_catalog_archive_mutation()`.
- Use restrictive/default dependency behavior, an explicit transaction, bounded lock acquisition, and error-on-failure execution. A failed dependency or lock check aborts the transaction. Confirm the migration runner's transaction handling and migration-history behavior in rehearsal.
- Preserve all core table data, identities, source presentation/order fields, constraints, indexes, RLS, and reader policies. The sole planned core-column removal is `source_row_id`.

Do not re-run this DDL outside migration bookkeeping. A clean installation may create the historical metadata tables transiently while replaying older migrations; its final schema must have none. No operational tool may depend on those intermediate tables.

## Test data and importer retirement

The existing `published_catalog` fixture and `serve_catalog_api.py` call `apply_plan`; `catalog_seed.py` inserts a batch; the verifier joins archive tables. These must be rewired before the importer can be deleted.

Capture an independent repaired core-data fixture from the pre-change disposable import, with stable natural keys, row-level presentation, multiplicity, and order. Preserve original source/repair files unchanged. A local-only seeder in `backend/scripts/catalog_seed.py` writes only core tables and can operate before and after removal. It must validate its local disposable target; merely naming a function “seed” is insufficient.

Maintain a legacy upgrade fixture in `backend/tests/fixtures/pre_catalog_removal.sql`, captured while the old importer is still available. It exercises real source-row foreign keys, archive triggers, and provenance relationships. Load it only into a database stopped at migration `20261022000300`; then apply the new migration. The steady-state seeder and final regression setup do not import or execute `scripts.import_catalog`.

Prefer a small canonical core-data snapshot helper for tests and read-only comparison over a replacement production import framework. Compare by stable keys and row multisets rather than generated IDs for cross-database fixture parity; compare IDs as well for before/after mutation on the same database. Source-file provenance checks can remain offline where meaningful, but database provenance persistence tests must be replaced with migration/data-preservation tests.

## Production execution and recovery

Discover the current linked project and match it to the documented public identifier and deployment environment without printing secrets. Confirm migration history and all dependencies. Pause direct writes and imports during final baseline/export/migration/post-DDL comparison, or establish an equivalent consistent snapshot boundary. This prevents valid user edits from being mistaken for migration loss.

Store a consistent full application schema/data export in private storage outside Git, with timestamp, file digest, object counts, and a tested restore procedure. A raw data dump alone cannot recover dropped schemas/constraints. Also retain `source_row_id` values keyed by mapping ID and sequence state for recovery. Do not commit production dumps, connection strings, or credentials. Record only redacted evidence and the private artifact reference.

Rehearse restoration in an isolated database and compare core and archive contents. Distinguish recovery of deleted metadata from rolling back application code. After removal, the old PostgreSQL adapter fails because it requires the deleted batch table. Prefer the compatible runtime or explicit JSON fallback for service recovery; restore database metadata before attempting an old-runtime rollback. JSON rollback serves the frozen original snapshot and can reverse documented repairs. A real data restore requires controlled writes and a review of edits made after the export; do not blindly overwrite newer production records.
